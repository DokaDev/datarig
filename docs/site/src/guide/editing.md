# Editing data

The rows of a result can be changed in the grid: a cell's value, new rows, rows to delete.
Nothing is sent while you edit. The changes stay pending on the result until you look at the
statements that apply them and say yes; then they run in one go, each row checked first.

## What can be edited

The first key that changes a cell or a row reads the table's details fresh (the status bar
says "Loading the table's details…") and then does what was pressed. From then on the result tab
strip says what the rows are to editing: `editable · shop.users · key id` (the key that finds a
row), `rows matched by values` (no key in the result: a row is found by the values it shows), or
`read-only · <reason>` for a reason about the statement, the table or finding the rows. The
other reasons below, the connection's among them, are said by the key only.

A result is editable when its statement is one `SELECT` of one plain table, its connection is
open and may write, and its rows can be found again. A pressed key that cannot do its work says
"Read-only: …" or "Can't edit: …" and changes nothing. The reasons are:

- **The statement.** It is not a single `SELECT`; it uses `WITH`; it reads more than one table
  (a join or a comma in `FROM`); it has a subquery in the select list or in `FROM`; it combines
  results (`UNION`, `INTERSECT`, `EXCEPT`); it groups rows (`GROUP BY`, `HAVING`, `DISTINCT`,
  `DISTINCT ON`); it uses a window function; `FROM` names no plain table (a function,
  `LATERAL`, `VALUES`, a sample) or there is none; its columns do not come from the table named
  in `FROM`; it reads a view.
- **The table.** Its columns are not known yet (the keys are still being read, or could not be
  read), or it is not known at all (created outside the app: the explorer's refresh reads it
  again); no column of the result is a column of the table; the rows are not of a plain table
  (a view, a materialized view or a foreign table); the table changed since the query ran; its
  details could not be read.
- **Finding the rows.** No column of the result compares exactly, so its rows can't be found
  again (see [How a row is found](#how-a-row-is-found)).
- **A selection.** Its cells are of more than one column ("Select cells of one column to edit
  them together"); it holds both new rows and rows read ("Select new rows or rows read, not both,
  to edit them together"); `D` on whole columns ("Select rows (V) to delete them, not whole
  columns").
- **The connection.** The tab's connection is not open; the connection's environment is
  read-only (or was when the tab's session opened); this connection type can't edit data; the
  connection changed since these rows were read (run the query again).
- **A column.** It is computed in the query, not a column of the table; it is generated by the
  database; it is `GENERATED ALWAYS AS IDENTITY` (it takes no new value in a row read, but a new
  row may give one); it is shown more than once.
- **A value.** A row is not shown whole, so it can't be found again; a column's values (or one
  value) are not shown as stored, for example text read in another character set than `utf8mb4`
  or a MySQL `TIMESTAMP` in a time zone that is not a fixed offset; a MySQL `FLOAT` column is
  shown rounded, so its selected cells are not typed together (one at a time is); a row could
  not be read; a row is marked for deletion; no column of the result takes a value in a new row.
- **While applying or after.** The pending changes are being applied; changes were applied to
  these rows (re-run the query to edit them); the table's details are no longer known while
  changes are pending (run the query again).

## Keys

In the grid:

| Keys | What it does |
|---|---|
| `e` (`Space d e`) | Edit the cell, or the selected cells of one column |
| `Space d n` | Set the cell (the selected cells) to NULL |
| `Space d D` | Set the cell (the selected cells) to the column's default |
| `o` (`Space d o`) | Add a new row, every value its column's default |
| `O` (`Space d O`) | Add a new row with the values of the cursor's row |
| `D` (`Space d d`) | Mark the row (the selected rows) to be deleted, or unmark it; a new row is removed |
| `Space d r` | Drop the pending changes of the cell (the selection) |
| `u` (`Space d u`), `Ctrl+R` (`Space d U`) | Undo, redo |
| `Space d p` (`:changes`) | Show the pending changes in the [Changes tab](#the-changes-tab) |
| `Space d a` (`:apply`) | [Apply](#apply) them, once asked on the status line (in a dialog when one is needed) |
| `Space d x` (`:discard`) | Drop every pending change of the result (it asks first) |

The full lists are in the keybindings reference: the [grid](../reference/keybindings.md#grid),
the `Space d` group under [nav](../reference/keybindings.md#nav), the
[cell editor](../reference/keybindings.md#gridedit-text), the
[editor of several lines](../reference/keybindings.md#overlaycell_editor-text), the
[Changes tab](../reference/keybindings.md#changes), the
[status line question](../reference/keybindings.md#statusask) and the
[Apply dialog](../reference/keybindings.md#overlayedit_preview).

While changes are pending the strip shows `3 pending` and a Changes tab, and the hint line
offers `Space d a` apply and `u` undo. A pending change is a row: a row read with changed cells (two cells of one
row are one change), a new row or a row to be deleted. The row number's gutter marks them `~`,
`+` and `-`. Changed cells take their own color, new rows another, rows to be deleted are
crossed out, and a cell left to its default shows a dim `default` (theme tokens
`edit_changed`, `edit_inserted`, `edit_deleted`, and `edit_pending` for the count; see
[Theme files](../reference/theme-files.md)).

### With the mouse

A right click on a cell selects it and opens the action menu; inside a selected range it keeps
the range, and the menu is the selection's (`Space Space` opens the same one next to the
selection). Its first section lists the edits after the copies, each with its key: edit the
cell, set it to NULL or to the column's default, add a row, add a copy of the row, mark the row
to be deleted; once changes are pending, undo, showing the changes (the Changes tab) and
dropping them. On a new row it lists only its edits: nothing there reads a row of the result. An item
runs as its key does.

The menu lists only the edits whose keys would act: each is checked as its key checks before
it changes anything. A result that can't be edited (a join, a read-only environment, a
connection that is not open, a connection type that can't edit data) offers no edits but
undoing or dropping the changes already pending. A selection of several columns offers no edit
of cells, whole columns no deletion, and a row marked to be deleted no change of its cells.
Until the first edit key has read the table's details, what its columns take is not known yet:
the menu then offers NULL and DEFAULT on any column, and the key says why when one refuses it.

## The cell editor

`e` opens a line over the cell with its pending value, or its value as read. A NULL or a
pending DEFAULT opens as an empty line.

- `Enter` keeps the text. An empty text is the empty string, never NULL: `Ctrl+N` and `Ctrl+D`
  set NULL and DEFAULT again.
- `Esc` cancels; so does a click outside the line.
- `Ctrl+L` takes the text typed so far to the editor of several lines.
- With cells of one column selected, each takes the value, as one change (`u` undoes it).
- An enum or boolean column lists its values instead, then NULL and `DEFAULT` where the column
  takes them.

NULL is refused in a `NOT NULL` column. In a row read, DEFAULT is refused when the column has
no default, and when its default would take a new number (an identity, `AUTO_INCREMENT`, a
sequence): type a value instead. A new row takes any column's default.

### Values of several lines

A value with line breaks, and a JSON column's, opens in a box with the query editor's vim keys
instead (`Ctrl+L` gets there from the line too). In Normal mode `Enter` or `:w` (`:wq`, `:x`)
keeps the text, `Esc` or `:q` (`:q!`) cancels; `/` searches and `:s` substitutes as in the
query editor. A value whose line breaks are all `\r\n` keeps them; one that mixes kinds of line
break is refused ("mixes kinds of line break; it can't be edited here"). The one-line editor
does not take a paste with line breaks.

### Value checks

A typed value must be a value of the column's type, in the form the grid shows it; it is
refused, with the reason, when it would be stored as something else. Some of the reasons:

- "not a whole number", "out of the range of smallint", "not a number", "more digits than
  numeric(6,2) holds"
- "not true or false", "not a UUID", "not one of the column's values"
- "not a date (YYYY-MM-DD)", "not a date and time (YYYY-MM-DD HH:MM:SS)", "more than 3 digits of
  a second" (a PostgreSQL value with a time zone needs its offset, such as `+09`)
- "longer than 20 characters", "ends in spaces, which a CHAR column drops" (MySQL)
- "not bytes as shown: \x and hexadecimal digits in pairs" (MySQL: `0x` and upper-case digits)
- "real would store it rounded, as …" (a floating-point value must read back as typed)

What the app cannot judge, such as a check constraint, is left to the server.

## New rows

`o` adds a row with every value its column's default. `O` copies the cursor's row (its pending
values, else as read), except what the table gives a new row itself: the key's columns, a
number drawn (an identity, `AUTO_INCREMENT`, a sequence), generated and computed columns are
left to their default. A value that is not shown whole is not copied: the clone is refused,
naming the column.

**New rows appear at the end of the result**, after the rows read, in the order they were added
(on a new row, `o` and `O` put the next one right after it). The cursor goes to the new row.
`D` on a new row removes it. A new row has no number in the gutter; the messages number it after
the rows read ("Row 4" after three rows).

The preview refuses a new row that leaves a `NOT NULL` column without a default to its default
("Row 4: name is NOT NULL and has no default; give it a value"), and one of a table with such a
column that the result does not show ("…is not in the result; add it to the SELECT").

## Undo, revert, discard

- `u` undoes the last change of the result and `Ctrl+R` redoes it. A change of several selected
  cells, a delete of several rows and a discard are one step each.
- `Space d r` drops the pending changes of the cell, or of the selection: a value goes back to
  the value as read, a row marked to be deleted is no longer marked, and **a new row's cell goes
  back to its default** (a cloned row's too, not to the copied value).
- `Space d x` (`:discard`) asks "Drop the pending changes?": `y` drops them, `n` or `Enter`
  keeps them.

## The Changes tab

While the shown result has pending changes, the result tab strip has a **Changes** tab after its
result tabs: `Changes 3`, or `Chg3` where the strip is narrow. A narrow strip keeps it while it
fits next to the shown tab and Messages. `Space d p` (`:changes`) shows it with the focus; `H`
and `L` (`Space r [` and `Space r ]`) reach it as any result tab. It shows the changes of the
result last shown in the grid. After an Apply it stays, as `Applied` (`Appl`), to show what was
applied (see [After an Apply](#after-an-apply)); it goes once nothing is pending and nothing was
applied, or when the query runs again. When another result of the tab
has pending changes too, its second line says so: `Result 2 also has 1 pending`.

Its first line names the result and the table, and says how many updates, inserts, deletes and
problems there are. Then one line per change, deletes first, then updates (a line per changed
cell), then new rows:

```text
 Changes — Result 1 · shop.users                        2 updates · 1 insert · 1 delete
 - id=2   delete
 ~ id=1   email     'a@x' → 'z@x'
 ~ id=3   nickname  'cy' → NULL
 + new 1  id=DEFAULT · email='n@x' · nickname=DEFAULT
```

- The marks are the gutter's: `~` a changed cell, `+` a new row, `-` a row to be deleted, in
  their colors (`edit_changed`, `edit_inserted`, `edit_deleted`); they read without colors too.
- A row found by its key is named by the key's values (`id=2`, `a=1,b=2`); a row found by its
  values by its row in the grid, `row 31  (located by its values)`; a new row by its place
  among the new rows, `new 1`.
- Values are literals as they were read and as they are to be (`'text'`, `NULL`, `DEFAULT`), a
  long text cut at 40 characters with `…`, as the statements read them back. A line longer than
  the pane is cut with `…`.
- Every reason the changes can't be applied yet comes first, marked `!`, for every row (not
  only the first): a new row's `NOT NULL` column without a default, a row that matches no row or
  several rows, a count that failed. A row that matches several identical rows is listed too:
  which of them to change is asked when you apply.

`j` and `k` select a line, `Ctrl+D` and `Ctrl+U` move half a page, `g g` and `G` go to the first
and the last. `Enter` shows the line's row and column in the grid (a row the grid no longer has
is said). `u` and `Ctrl+R` undo and redo, and the `Space d` keys work as in the grid: an edit of
a cell goes to the grid at the selected line's cell first. Under the list the tab says how the
Apply stands to a transaction (as the Apply dialog's footer does), and its keys where they fit.

### The SQL view

`s` switches between the list and the statements that apply the changes, for the rest of the
run. `ui.changes_view = "sql"` (`:set ui.changes_view=sql`, or the settings screen) opens the tab
in the statements; `"list"` is the default. The statements are shown as the Apply dialog shows
them: in the order they run, in the editor's syntax colors, each with the count it must give
(`expect 1`) at the end of its first line, a statement longer than the pane wrapped under its
first line.

On MySQL a text value is compared by its UTF-8 bytes, so the statement holds it as
`_utf8mb4 X'…'`. A statement with such values is followed by a dim line that starts with `↳`
and reads them back in order, `column = 'text'` (a long text cut with `…`; bytes that are not
UTF-8 text say how many there are), grouped by where they are: `set` for the values an update
writes, `where` for those a row is found by, `values` for those an insert adds. An update can
name a column in both, its new value and the one it is found by:

```text
  UPDATE `shop`.`people` SET `note` = _utf8mb4 X'615C62' WHERE  expect 1
    `id` <=> 1 AND `name` = _utf8mb4 X'706C61696E206E616D65' AND
    CONVERT(`name` USING utf8mb4) COLLATE utf8mb4_0900_bin <=> _utf8mb4
    X'706C61696E206E616D65' AND `note` = _utf8mb4 X'6F6C64' AND
    CONVERT(`note` USING utf8mb4) COLLATE utf8mb4_0900_bin <=> _utf8mb4
    X'6F6C64'
    ↳ set note = 'a\b' · where name = 'plain name', note = 'old'
```

That line is not SQL: it is never sent to the server, and `c` copies the statements exactly as
they are sent, without it. A literal longer than a few hundred bytes is also shown shortened, its
start and end around how many characters are left out (`…786400 more characters…`); it is copied and sent
whole.

- **Row checks (lock, no waiting)** first: for every row read that changes, a `SELECT … FOR
  UPDATE NOWAIT` that finds and locks it. A row another session holds fails at once instead of
  waiting.
- **Writes**: the deletes, then the updates, then the inserts. A `DELETE` and a statement that
  expects more than one row are marked `!`, their count in the warning color.

`c` copies every statement exactly as it is sent, each followed by `;` and a line break (through
the `clipboard` setting), in both views. While the statements are not final it copies nothing
and says why: "Not copied: the SQL is not final yet: 2 problems", or "…: the rows are still
being counted".

Rows found by their values are counted on the tab's own session while the tab is shown, half
a second after the last change, once for each state of the changes ("Counting matching rows…"
until the answers come; the count sees the tab's open transaction, as the Apply does). The list
needs no count.

## Apply

`Space d a` (`:apply`, or "Apply the pending changes" in the action menu) works from the grid
and from the Changes tab. The rows found by their values are counted afresh first, every time,
whatever the Changes tab counted before; the count sees the tab's open transaction, as the
Apply does. The status bar says `Checking 3 rows…` until the answers come. Meanwhile any key
(`Esc` too), a click, the wheel or a paste stops waiting ("Apply cancelled") and does nothing
else, so none of them is taken by the question that follows; a dialog that opens or a run in the
tab cancels it too. Changes that move before the answers come drop the Apply: "Changes changed —
press Space d a again".

When the changes can't be applied yet, nothing is asked: the Changes tab takes the focus with
the first problem selected, and the status bar says "Can't apply: 2 problems — see Changes".
The problems are those of the list above, for instance:

- "Row 3 matches no row of the table now: it was changed or deleted. Re-run the query."
- "Row 3 matches 2 rows; add the key to the SELECT to edit it": the rows may differ in what the
  result does not show.
- "Row 3: email is not shown whole, so the row can't be found again", and the `NOT NULL` refusals
  of new rows above.

Otherwise the status bar asks, on one line in the warning color:

```text
Apply 3 changes to shop.users (2 updates · 1 delete)?  y apply · any other key cancels
```

Only `y` applies. Any other key (`Enter`, `Esc`, `n`, any letter), a click or a paste cancels
("Apply cancelled") and does nothing else: it never reaches the grid. Where the window is narrow
the question leaves out the table, then the kinds but the deletes, and at its shortest is
`Apply 3 changes (1 delete)? y/n`, the deletes always named. With
[manual commit](manual-commit.md) the question also says how the Apply stands to a transaction
("Opens a transaction; nothing is committed.", or "Runs inside the open transaction; nothing is
committed."); the shortest form says it too: `Apply 3 changes (1 delete), nothing committed? y/n`
or `…, in the open transaction? y/n`. The question is for the changes as they were asked about: a change, another tab,
a run, a transaction that begins or ends, or a lost connection drops it ("Apply cancelled: the
changes changed").

### The Apply dialog

A dialog, "Apply changes — shop.users", takes the place of the question when the statements
must be seen before `y`:

- a row matches several identical rows: "Row 3 matches 2 identical rows", with "[1] just one
  [a] all 2". The table has no key, the result shows every column, each comparing exactly, and
  the rows are the same in all of them. `1` changes one of them, `a` all of them (the write then
  expects 2).
- the last Apply's result is unknown (below): the first `y` warns, a second `y` applies again.
- the profile's [environment](environments.md) asks before every write (`confirm = "writes"`):
  the dialog is that question, no second one opens.

Cancel has the focus: only `y` applies. The dialog shows how many updates, inserts and deletes,
then the statements as the SQL view shows them; `j` and `k` scroll line by line, `c` copies them,
`Enter`, `Esc` or `q` closes. It closes by itself when its result, its rows' connection or the
changes change. Its footer says how the Apply stands to a transaction:

- "Runs in one transaction; commits at the end." (automatic commit)
- "Opens a transaction; nothing is committed." ([manual commit](manual-commit.md), none open)
- "Runs inside the open transaction; nothing is committed." (your own `BEGIN`, or a manual
  commit transaction already open)

### How a row is found

A row read is found by the table's primary key, or a `NOT NULL` unique key, when the result
shows all its columns and each of them compares exactly; else by the values of its columns that
compare exactly. A table others inherit from is always found by values. Floating-point numbers,
JSON, XML, geometry and types the app does not know do not compare exactly, nor (PostgreSQL)
arrays, intervals, a `numeric` without a scale, times with a time zone and network addresses,
nor (MySQL) text in a character set that does not convert one to one. Values are compared byte
for byte, never by the column's collation. An update also checks that each changed column that
compares exactly still holds the value read, and a delete every column that compares exactly: a
row changed elsewhere in those columns since is not overwritten.

### While it runs

`y` sends every statement on the tab's own session. While it runs the strip says `applying…`,
the Changes tab says "Applying 3 changes…" over the statements being sent, edit keys are
refused, and the query's cancel key (`Ctrl+C`) cancels it. When the result's pages are held
open, the cursor is closed first; the rows already read stay.

Either every statement gives its count and the changes are applied ("Applied 3 changes"), or
nothing is ("Nothing was applied", the changes stay pending and may be applied again). Why is said
on the Changes tab's second line, and in its SQL view the statement that failed is marked `!` and
scrolled to. A row found by a key is named with it ("Row 3 (id = 5)"), and a statement in a
message is its first line, cut short when long:

- "Row 3 was changed or deleted since it was read. Nothing was applied. Re-run the query to see
  the current values."
- "Row 3 now matches 2 rows, not 1. Nothing was applied."
- "Row 3 is locked by another session. Nothing was applied."
- "Row 3: <the server's error>. Nothing was applied. Statement: <the statement>"
- "Apply cancelled; nothing was applied."
- "Apply result unknown — the connection was lost before the server confirmed. Re-run the query
  to check." The changes may be in the table already: the next Apply opens the dialog, whose
  first `y` warns, and only a second `y` applies them again.

## After an Apply

The result shows what the Apply did over the rows as read, until the query runs again: written
values in italic (theme token `edit_applied`), deleted rows crossed out, the rows added after the
rows read. The strip says `applied` (`applied · not committed` while its transaction is open,
where it fits). These rows are not edited again: run the query first.

The Changes tab stays as `Applied`, until the query runs again: its list is what was applied,
its SQL view the statements that were sent (`c` still copies them), and its second line says
"Applied · re-run to refresh", or "Applied · not committed" while the transaction is open.

- PostgreSQL returns each written row as stored, so a value a trigger set shows too. A value in
  a form the grid shows differently (dates and times, floats, intervals, bytea, network
  addresses, most arrays) shows a dim `re-run to see`.
- MySQL returns no rows: a new row's `AUTO_INCREMENT` column shows the number it took, other
  defaults stay `default`.
- Paging on past the rows already read is refused ("Changes were applied to these rows: re-run
  the query to see the rest"): the rows the server would skip have moved.

With manual commit, or inside your own transaction, the Apply is not committed ("Applied 3
changes; not committed yet"): the status bar
counts it in the open transaction, and `:tx` lists it as "Apply (3 changes)". A commit keeps the
values shown; a rollback drops them ("The transaction was rolled back; the applied changes are
gone"), and the Changes tab says so until the query runs again. See
[Manual commit](manual-commit.md#editing-data).

## Leaving with changes pending

Running a statement in the tab (its results are replaced), closing the tab and quitting ask
first when changes are pending, saying how many: `y` drops them and goes on, `n` or `Enter`
keeps them and does nothing. Changes already applied do not ask; an open transaction asks as
usual. Deleting a connection profile or a saved query closes its tabs without another question:
its own question says how many pending changes go ("2 pending changes of the results are
dropped.").

## Copy and search

Copying (`y`, `Y`, the `Space r y` group, `:copy`), the search (`/`, `?`), the cell viewer
(`Enter`) and the inspector take the values the grid shows: a pending value or what an Apply
wrote, not the value read. A copy with pending values says "(with pending changes)", and counts
the copied rows marked to be deleted, which are copied as shown.

- A pending DEFAULT has no value yet: a copy of it is refused, except as SQL `INSERT`, which
  writes `DEFAULT` there. A cell showing `re-run to see` is not copied, nor is one an Apply set
  to its default, shown `default` ("Not copied: nickname shows “default”; run the query again to
  copy its value").
- New rows are not copied ("A new row is not copied: it is not a row of the result yet") and the
  search does not look at them.

## Export and the chart

An export to a file and the chart do not take the values the grid shows over the rows:

- An export of the rows held (the selection, the fetched rows, or every row of a result fetched
  to its end) is refused while the result has pending or applied changes ("Not exported: this
  result has pending changes; apply or discard them, or run the query again — see Changes"; with
  changes applied, "Not exported: this result has pending or applied changes; apply or discard
  them, or run the query again"), in every format.
- An export of every row of a result the server has more of reads the rows again from the
  server, so it holds what an Apply wrote. With changes pending it goes on, and says "The pending
  changes are not in the file: every row is read again from the server".
- The chart draws nothing while the result has pending or applied changes: it says "Not drawn:
  this result has pending changes. Apply or discard them, or run the query again — see Changes",
  or, once they are applied, "Not drawn: this result has pending or applied changes. Run the
  query again to chart the edited values."
